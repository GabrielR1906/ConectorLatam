Documento de Arquitectura de Software: ConectorLatam
Este documento consolida las decisiones de diseño técnico y la infraestructura en la nube para el desarrollo de ConectorLatam. Está diseñado para servir como punto de partida para la implementación del código base y la provisión de infraestructura.
1. Visión General del Sistema
ConectorLatam es un sistema ETL (Extract, Transform, Load) bajo el modelo SaaS, operando en una arquitectura Serverless y orientada a Microservicios. Su objetivo principal es la extracción automatizada de comprobantes electrónicos desde entidades fiscales latinoamericanas (SRI, SAT, SUNAT, DIAN) y su carga directa en Data Warehouses (BigQuery, Snowflake, Redshift).
2. Infraestructura Base (Google Cloud Platform)
Componente / Servicio	Propósito en la Arquitectura
 
Cloud Run	Cómputo principal. Alojamiento de los microservicios (contenedores Docker) que ejecutan la lógica de extracción (Python) y carga. Escalamiento a cero y regionalización por país.
Firestore	Base de datos operativa (NoSQL). Almacena configuraciones de pipelines, historial de ejecuciones y estado en tiempo real para alimentar el Dashboard interactivo.
Firebase Authentication	Gestión de identidades y accesos. Implementación de Custom Claims para separar roles de Administración (acceso total a monitoreo) y Clientes (aislamiento de datos).
Cloud Tasks	Enrutamiento regional y Limitador de Tasa (Rate Limiting). Organiza las peticiones salientes a las APIs gubernamentales para evitar baneos por exceso de tráfico.
Google Secret Manager	Bóveda criptográfica. Almacenamiento exclusivo de credenciales sensibles (certificados .p12, FIEL, RUC/Claves).
Cloud NAT	Asignación de IPs estáticas de salida. Esencial para cumplir con los requerimientos de "Whitelisting" (Listas Blancas) en los firewalls de los gobiernos.

3. Topología de Microservicios
●	MS-API-Gateway: Expone la API REST documentada en OpenAPI/Swagger. Maneja las peticiones de los clientes, valida tokens JWT generados por Firebase y dirige el tráfico internamente.
●	MS-Extractor (Patrón Adapter): Servicio en Python. Contiene un motor central y adaptadores modulares para cada entidad fiscal (SRI, SAT, SUNAT, DIAN). Gestiona la lógica de autenticación específica del país, paginación, y manejo de errores.
●	MS-Loader: Microservicio encargado exclusivamente de recibir los datos limpios estandarizados y orquestar la inserción masiva hacia Google BigQuery, Snowflake o Amazon Redshift, respetando el esquema predefinido.
4. Ciclo de Vida del Dato (El Pipeline ETL)
1.	Configuración: El cliente configura una extracción desde el Frontend. La periodicidad y destino se guardan en Firestore. Los certificados se alojan en Secret Manager (Firestore solo guarda la referencia).
2.	Disparador (Trigger): Cloud Scheduler (para ejecuciones programadas) o la API emite un evento a Cloud Tasks.
3.	Orquestación: Cloud Tasks aplica los límites de tasa y enruta la petición a la instancia regionalizada de Cloud Run adecuada.
4.	Extracción y Transformación: MS-Extractor recupera el secreto en memoria, consulta la API fiscal, aplica los filtros, normaliza los datos y cambia el estado en Firestore a en_proceso.
5.	Desacoplamiento: Los datos normalizados fluyen a través de un bus de eventos (Pub/Sub) hacia el siguiente servicio.
6.	Carga y Finalización: MS-Loader procesa el evento, inyecta los datos al DWH. Al finalizar, actualiza Firestore con el estado completado, y los registros procesados, lo cual impacta instantáneamente el Dashboard del cliente.
5. Seguridad y Estrategia Gubernamental
●	Reglas de Seguridad de Firestore: Un cliente solo tiene acceso de lectura/escritura a sus propios documentos, asegurado a nivel de la base de datos mediante el UID de autenticación.
●	Monitoreo de Salud: Priorización de monitoreo pasivo mediante el registro de éxito/fallo de peticiones reales para prevenir penalizaciones por polling excesivo a las entidades gubernamentales.
●	Cifrado: Transmisión asegurada con TLS 1.3 y credenciales estrictamente fuera de la base de datos principal.
